<objective>
Run the three-install sign-in sequence that is this phase's actual gate (PKG-04, PKG-05, and the
ROADMAP Phase 1 Gate question about side-by-side install). This is a physical-device verification
plan — no task here is agent-automatable. Every task is a checkpoint the operator executes and
reports back on with specific, named evidence.

Purpose: PKG-05 is explicitly "a gate, not a checkbox" (REQUIREMENTS.md) — sign-in survival is
community inference, not proven mechanism (PITFALLS.md verdict), so it must be proven on a real
device with a real account before any later phase (hook validation, ad additions, downloads)
is trusted to build on top of a working install. The three-install order is fixed and must not
collapse: each step's failure has exactly one attributable cause (packaging, then a hook, then the
bundle-ID question).
Output: three device-verified results, captured in this plan's SUMMARY: inert sign-in
pass/fail, live sign-in pass/fail, changed-bundle-ID sign-in pass/fail plus what that implies for
PROJECT.md's "no side-by-side install" Key Decision.
</objective>

|----------|--------------|
| Real Google account signing in on a re-signed, third-party-team-ID-signed binary | Accepted project risk — attestation/integrity enforcement on the auth path is unresolved per PITFALLS.md and has no client-side fix if Google tightens it |
| Changed-bundle-ID test app | Must be visually distinguishable from the production Bramble install to avoid the operator confusing the two on a shared device |

| T-01-13 | (accepted risk) | Google sign-in under a re-signed, non-Google-team-ID binary | accept | Already an accepted, documented project risk (PITFALLS.md verdict) with no client-side mitigation available; this plan's entire purpose is to observe, not to fix, this risk |
